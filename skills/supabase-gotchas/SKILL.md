# Supabase

Extracted from the global CLAUDE.md on 2026-07-26 as part of the
Claude 5 progressive-disclosure prune. These are gotchas, not conventions.

- user creation: GoTrue `/auth/v1/signup` - never raw SQL INSERT into `auth.users`
- Next.js: `@supabase/ssr` (NOT `@supabase/auth-helpers-nextjs`) for cookie-based auth in App Router
- edge functions: CORS headers on ALL response paths including errors; wrap `req.json()` in try/catch; `AbortController` timeout on every external fetch (30s LLM, 15s APIs)
- edge functions shared code in `supabase/functions/_shared/` (underscore = not deployed); import via `../_shared/foo.ts`
- edge function sub-path routing: `functions/v1/my-func/any/sub/path` routes to `my-func`; full URL in `req.url`
- anonymous → registered upgrade: `auth.updateUser({email, password})` - `linkIdentity()` is OAuth-only
- anonymous sign-in + `handle_new_user` trigger: any NOT NULL column referencing `NEW.email`/`NEW.phone` crashes anon signup - `COALESCE(NEW.email, '')` and allow NULL on profile email
- fresh-project grants: Management API migrations don't auto-grant CRUD. Grant only the DML each role needs (`GRANT SELECT, INSERT, UPDATE, DELETE ... TO authenticated`, plus `service_role`) and set `ALTER DEFAULT PRIVILEGES` to match. NEVER `GRANT ALL` to `anon` or `authenticated`: ALL includes TRUNCATE, REFERENCES, TRIGGER and (Postgres 17) MAINTAIN, and TRUNCATE ignores RLS and row triggers. Proven on local CLI 2.106.0: postgres-owned public tables default to `authenticated=Dxtm` in `pg_default_acl`, a migration that revokes only INSERT/UPDATE/DELETE leaves TRUNCATE in place, and a signed-in user's `TRUNCATE appointments CASCADE` wiped every tenant. On that build `service_role` got NO DML by default, so grants depend on project age. Make migrations set every privilege explicitly (`REVOKE ALL ... FROM anon, authenticated` first) and assert with `information_schema.role_table_grants`.
- fresh-project auth providers: anon + email/password + most social default OFF (Auth → Providers) - migrations can't toggle them; ALWAYS dashboard-sweep before testing. Confirm-email defaults ON when Email is on - turn OFF unless app has verify-email screen + deep link.
- QA test user provisioning: `POST /auth/v1/admin/users` with service-role + `email_confirm: true`; Email provider toggle still must be ON for `/token?grant_type=password`
- Supabase + Expo storage: `Platform.OS === 'web'` check with `require('expo-secure-store')` lazy import for native, `globalThis.localStorage` for web - top-level `import * as SecureStore` crashes on web
- Supabase Edge Functions (Deno): exclude from tsconfig `"exclude": ["supabase/functions/**"]` - Deno imports cause TS2307/TS2304 in Node tsc
- esm.sh version-pinned Supabase clients are NOT nominally compatible: `@supabase/supabase-js@2` and `@2.49.1` resolve to DISTINCT SupabaseClient classes, so passing one where the other is typed fails on protected members (TS2345). Type the seam structurally (`type DbClient = { from(table: string): any }`) instead of importing the class from a second pinned URL
- Supabase PostgREST builder: `.rpc()` returns `PostgrestFilterBuilder`, not a real Promise - can't `.catch()` directly; await first or wrap in try/catch
- that same builder NEVER REJECTS unless `.throwOnError()` is set: it resolves to `{data, error}` even on an AbortError (verified 2026-08-12 by reading the pinned esm.sh sources, 2.107.0 + 1.19.2). So `Promise.resolve(builder)` is a SAFE way to start an independent read early and `await` it after other work, with no unhandled-rejection hazard - the recipe for overlapping a read with a write inside one edge function invocation. The statement ordering between start and await is load-bearing (the read must not need the write's result); comment it as such or a later refactor will reorder it.
- Supabase `functions.invoke` auth header is VERSION-DEPENDENT, so verify against the installed lib before touching `verify_jwt`: supabase-js 2.112.3 injects the SESSION access token as the bearer (`dist/index.mjs` sets `omitApiKeyAsBearer: true`), so a signed-in caller passes `verify_jwt` fine and `--no-verify-jwt` REMOVES a real defense. The older "sends anon key, not user JWT - deploy with `--no-verify-jwt`" advice was true of earlier versions and cost nothing to disprove: grep the installed dist for how the Authorization header is built. A stale version of this exact bullet sat in a project stack-guidance file and nearly stripped the gate.
- Supabase expired refresh token: wrap `getSession()` in try/catch in auth store `initialize()` - expired tokens crash app
- PostgREST embed returns a to-ONE OBJECT (not an array) when the FK column is ALSO the table's PRIMARY KEY (`user_id PRIMARY KEY REFERENCES profiles`) - `?.[0]` then silently yields `undefined` on EVERY row; masked live because every row fell through to the same wrong default. Check the embed's actual shape, don't assume array.
- PostgREST upsert + partial unique index: `.upsert({onConflict: 'col1,col2'})` silently returns 0 rows if the index has a WHERE clause - use full (non-partial) unique index
- `supabase functions deploy` flips `verify_jwt` to TRUE when `config.toml` declares no per-function config, even if prod runs false - a bare deploy 401s a live admin caller. Check the drift BEFORE deploying, pass `--no-verify-jwt` explicitly, verify after via the Management API.
- a DEPLOYED edge function's served body is a BINARY eszip, so a plain `grep` for a source marker finds nothing and reads as "my code never deployed". Use `grep -a`, and always pair it with a control string that SHOULD be absent so a silently-broken grep cannot read as a pass.
- Supabase `generateLink()` SENDS NOTHING - it only mints the link. Password reset needs the actual send-email API.
- assert the affected ROW COUNT after every privileged write (`.select()` + length check) - an RLS silent no-op otherwise reads as success
- `supabase secrets list` shows hashes only - deploy a throwaway edge function to read secrets server-side, then delete
- Supabase CLI multi-account: no profile support - `npx supabase login --no-browser` overwrites `~/.supabase/access-token`; re-login to switch back
- Supabase Storage bucket via API: `POST /storage/v1/bucket` with service-role + `{"id": "name", "name": "name", "public": true}`; then RLS policies via migration
- Supabase DDL with no CLI/DB-URL wired: POST `/v1/projects/{ref}/database/query` with the token at `~/.supabase/access-token` (service-role key can't run DDL); use `curl` (real UA) - Python-urllib gets Cloudflare 1010
- new read surfaces blocked on DB provisioning: ship Supabase-first with a static-seed fallback (try DB, catch -> seed) so the UI ships now and auto-upgrades at migration cutover with no surface code change
- cron/pg_net-triggered edge fn doing long work: return 202 + `EdgeRuntime.waitUntil` (pg_net kills the call at ~60s); keep a `?wait=true` sync path for QA
- pg_cron + vault: `cron.job.active=true` proves scheduling, not execution. A command that reads `vault.decrypted_secrets` for a name nobody inserted (`project_url`) fails EVERY tick with `null value in column "url" of relation "http_request_queue"` and nothing surfaces it (jobs stayed dead for weeks while hundreds of failures piled up). After any cron migration read `cron.job_run_details` for a SUCCEEDED row plus `net._http_response` status, and assert every vault name a cron command dereferences exists in `vault.secrets`. Count the rows a revived job will act on BEFORE inserting the missing secret.
- cross-invocation mutex/cooldown in edge fns: atomic conditional `UPDATE ... RETURNING` on a marker row (no new table); claim AFTER a candidate exists so empty runs don't burn the window
- "idempotent" is NOT "replay-safe" (this failed on a payment replay): an upsert-based guard silently no-ops when the target column has NO UNIQUE constraint (Postgres `42P10` on `ON CONFLICT`), and a read-then-write guard is a TOCTOU race under redelivery. For at-most-once on payment or webhook effects: add the REAL unique constraint AND consume via a SECURITY DEFINER compare-and-set RPC (service-role-only) that returns whether THIS call won; use upsert-not-update so a tolerated pre-terminal write still reconciles
- free-project quota is per-USER, not per-org, and counts every org where that account is an **administrator or owner** (limit 2 active free projects). So being promoted from Developer to Administrator to fix a create-permission `403` can immediately produce a `400` quota error naming your own account: the promotion is what pulled the new org into your personal quota scope. Clearing the first gate is what exposed the second. Resolution is upgrade the org off free, or have an Owner who has room create it while you are NOT an admin of that org.
- the Management API exposes **no plan field anywhere**: not on `/v1/organizations`, not on `/v1/projects`, not on the org-scoped projects route, and `/v1/organizations/{id}/billing/subscription` is a 404. `supabase orgs list` does not carry it either. You therefore CANNOT determine which projects consume a free quota programmatically; the dashboard is required. Beware parsing that 404 body into a plan variable, which yields a confident `plan=None` for every org.
- Edge Functions have NO static egress addresses, so IP-restricting a Google/vendor key held by a function is INFEASIBLE, not a to-do: any allowlist is a guess that blocks prod or admits the world. Do not write "IP-restrict the key" into a definition of done for a function-held key; the honest controls are API restriction at mint time (re-read from the API), secret-store-only custody (verify the key reaches no response/log path), verify_jwt plus an in-function bearer check, and a durable per-user rate limit. Record the substitution in decisions so no later pass re-opens it.
- GoTrue `/auth/v1/recover` rejects `example.com` addresses outright (`email_address_invalid`), and a 200 from it proves NOTHING about the redirect allowlist: a non-allowlisted `redirect_to` is silently swapped for the site URL rather than rejected. The allowlist proof from a headless box is the config read-back diff after the PATCH; the only behavioural proof is opening the emailed link, which is a device/inbox leg - name it as such instead of manufacturing a probe.
- An edge function's HTML response renders as RAW MARKUP on the default `*.supabase.co/functions/v1/` domain, because the platform serves it as plain text whatever `Content-Type` the function sets (an HTML success page showed `<h1>...` on screen, found only by screenshotting the real browser). Never make a function the landing page a human sees; 303 to a page on the app's own domain with a fixed result code, and allowlist that target as an https-only config value.
- OAuth providers append a fragment to the callback URL (a trailing `#_`), and a browser carries the REQUEST's fragment onto a 3xx `Location` that has none, so a redirect to `/appointments/confirm?result=x` lands as `/appointments/confirm#_?result=x` in an SPA router and the query is silently lost. End the `Location` in an explicit empty `#`. A unit test of the header string cannot see this: prove it by loading the live callback URL WITH the provider's fragment in a real browser and asserting the landed URL.
- A Free-plan project that has AUTO-PAUSED does not say so on the routes you probe first: `GET /v1/projects/{ref}/api-keys` returns an EMPTY list (200, not 403), `supabase projects api-keys` returns `[]`, and `database/query` answers 544 `Connection terminated due to connection timeout`, all of which read as a token, tenancy or outage problem. `GET /v1/projects/{ref}` shows `status: INACTIVE` and `/health` says `No active services available`. Read project status before diagnosing any of those. `POST /v1/projects/{ref}/restore` brought it back to `ACTIVE_HEALTHY` in about 2 minutes with keys, data and functions intact. Restoring counts against the org's Free active-project limit.
- Fixed SMS test codes are an Auth config pair, `sms_test_otp` (`15555550100=123456,...`, no plus sign) and `sms_test_otp_valid_until`, and they EXPIRE SILENTLY: after the timestamp the number just behaves like a real one, which a QA tester reports as "the test phone stopped working". The codes also apply to the `phone_change` verify path (email sign-up, then `PUT /auth/v1/user {phone}` and `verify type=phone_change`), proven live with a wrong-code control returning 403. One phone per user, so give QA several numbers. Separately, when a third-party SMS provider is in front, an international tester receiving nothing is usually that provider's messaging geo-permissions, not Supabase: one test send fails instantly with the provider's geo-permission error, the setting is often console-only (the API path 404s), and an account the operator does not administer needs its owner to change it.
- Deno `npm:` specifiers DO have a supply-chain age gate: `deno install --minimum-dependency-age=P7D --entrypoint <files>` (Deno 2.8, unstable flag) refuses versions newer than the cutoff, transitive deps included, and writes `deno.lock`. Pin top-level versions as well, because the hosted runtime resolves on its own.
- Running `supabase/edge-runtime:<ver>` directly via Windows `docker.exe` from WSL: bind mounts of WSL paths do not work, so `docker create` then `docker cp <dir> ctr:<container-home>/` (it lands as `<container-home>/<basename>`, check with `find`) then `start --main-service <container-home>/<fn>`. The container home is the image default, not your machine. Gate readiness on `docker inspect -f '{{.State.Running}}'`, never on a curl retry: Docker Desktop's port proxy accepts connections for an exited container, so a curl loop hangs for its full `--max-time` on each try. The CLI's pinned runtime version is in the binary (`grep -aoE 'supabase/edge-runtime:v[0-9.]+'`).
